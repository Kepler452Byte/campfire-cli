# 模糊任务 SOP

适用于领导口头交代、IM 转述、个人待办、要求 Agent 跟进或尚不完整的执行意图。

## 从原话到正式任务

```text
用户原话
  -> 识别来源、对象、期望结果和时间约束
  -> 搜索相关项目、已有任务和稳定文档
  -> 在当前对话形成任务建议
  -> 仅确认关键歧义
  -> 用户确认
  -> 交给任务治理创建并维护正式任务
```

任务草案至少应让用户确认：目标、范围、非目标、验收标准、项目归属和是否允许实施。缺少普通实现细节不阻止确认；会扩大影响或改变业务方向的问题必须前置。

用户明确说“记一下”“帮我跟进”时，可以在当前对话展示任务建议；只有用户确认创建或跟踪任务后，才读取 `mywork-task-governance` 创建正式任务。仅仅提到一件事情，不自动创建任务。

## 与项目工程 Task 的边界

Campfire 任务负责来源、负责人、跨 Session 状态、阻塞、审查和工作成果。软件项目内的 `tasks/TASK-*.md` 负责一次代码变更的 Goal、Scope、Constraints 和 Acceptance Criteria。

```text
Campfire Task = 工作协作事实
Project TASK  = 工程变更契约
Git           = 代码事实
```

进入软件实施前，关联而不是复制项目 Task。项目已有 `tasks/SPEC.md` 时遵守它；没有时不要擅自引入模板体系。稳定工程结论回写项目 SPEC，跨项目经验才提交为 Workspace 知识候选。

用户对记录或创建任务的授权不自动包含修改代码、发送外部消息、删除内容或扩大范围的授权。正式任务的生命周期、字段和人工确认边界只读取 `mywork-task-governance`，本 SOP 不复述。
