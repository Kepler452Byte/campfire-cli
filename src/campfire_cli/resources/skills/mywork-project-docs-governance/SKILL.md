# 项目文档中心治理

适用于 `mywork/` 下名为 `【项目】文档中心` 的、面向人和 Agent 阅读的 Markdown 项目文档。目标是让人从 MOC 索引进入，让 Agent 通过路径、文件名和 frontmatter 稳定检索。`assets/`、`a_skill/`、代码、生成物和只有附件而没有项目文档的目录不套用本规范，也不为它们强建 MOC。

## 信息模型

- 目录先标识项目，再标识稳定的业务或技术领域；不用 `docs/` 作为杂项收纳目录。
- 文件名以中文类型前缀开头：`产品-`、`技术-`、`决策-`、`计划-`、`问题-`、`记录-`、`看板-`，后接具体名词短语；Obsidian Kanban 工作台使用单选 `type: board`，插件字段 `kanban-plugin: board` 作为有值扩展字段保留。
- frontmatter 是机器可读分类的最终依据。所有项目文档必须使用同一份[字段契约](references/frontmatter-schema.md)，不得自行更改基础字段名、字段含义或枚举值。
- `status: current` 表示该文档是其类型的当前有效版本；它不表示计划已落地。`draft` 表示尚未生效；`archived` 仅作历史参考。
- `lifecycle` 独立记录工作状态。不得根据计划或记录推断当前系统行为。

## 目录与 MOC 规则

默认使用以下骨架，领域名称按项目实际词汇确定：

```text
【项目】文档中心/
├── _总览/
│   └── MOC-项目总览.md
├── <领域>/
│   ├── MOC-<领域>.md
│   ├── 产品-*.md / 技术-*.md / 决策-*.md / 计划-*.md / 问题-*.md
│   ├── 记录/
│   └── archive/
└── 记录/
```

默认将带类型前缀的文件直接放在领域目录。只有同一领域某类活跃文档长期过多、直接列出已无法阅读时，才建立类型子目录。`任务/`、`记录/` 与 `archive/` 是常规例外；任务高频变化且主要通过 Base 聚合，不应遮蔽当前权威文档。

每个项目维护一篇项目 MOC，每个领域维护一篇领域 MOC。MOC 先链接当前权威文档，再列进行中提案，最后列重要记录和归档。创建、移动、归档或替代文档后，必须同步更新相关 MOC。

## 两阶段归档

项目文档统一使用领域内扁平的 `archive/`，不按年份自动建立子目录。人类或 Agent 先在待归档文档的 frontmatter 中设置 `archive_requested: true`，并填写 `archive_reason`；若原因是 `superseded` 或 `merged`，还必须填写 `superseded_by`。标记阶段保留原有 `status` 和 `lifecycle`，不得提前伪装成已经完成归档。

先运行 `campfire archive check` 审查候选，再运行 `campfire archive apply --confirm` 执行。CLI 仅移动校验通过的候选，目标固定为同一领域的 `archive/<原文件名>`，并更新为 `status: archived`、`lifecycle: archived`、`archive_requested: false`，写入 `archived_at`。归档后运行 `campfire maintenance run` 同步并验收治理状态。

用户已经手工移入 `archive/` 的文档视为明确的人工归档，不移回当前目录；工具应将路径作为历史可见性的最终依据，并报告缺失或冲突的归档元数据。现有历史快照子目录允许保留，脚本不得主动创建新的年份或版本子目录。

## 工作流程

1. 迁移前先检查项目目录及其链接，形成逐文件映射：原路径、目标路径、`type`、`status`、`lifecycle` 和待确认项。
2. 领域划分使用用户已有的项目词汇，不为了套模板而虚构领域。
3. 新建文档时，先读取[模板字段说明](references/模板/字段说明.md)，再按类型选用同目录下的模板。该 Skill 的 `references/模板/` 是项目文档模板的唯一来源。
4. 改名时，赋予正确的类型前缀，并补齐或规范化 frontmatter。
5. 归档已完成的计划、修复或功能文档前，先将已验证结论回写到受影响的当前产品、技术或决策文档；再设置 `archive_requested: true` 和归档原因，存在替代文档时填写 `superseded_by`。
6. 移动或改名后，检查 wikilink、Markdown 链接、嵌入、附件，以及文档中心外部的引用；修复已确认失效的链接。
7. 验证当前文档、提案和历史材料都可通过文件名前缀和 frontmatter 分别检索。

## 边界

- 目录重组属于迁移。分类存在不确定性时，先保留可审阅的映射，再批量移动。
- 不得仅因长期未更新而归档；归档需要完成、被替代或用户明确指示作为依据。
- Agent 无法判断有效结论是否已经沉淀时，只能提出候选或报告问题，不得设置归档标记。
- `archive/` 中的文档不能作为当前项目事实依据。
- 没有当前文档佐证时，不得将 `计划-`、`问题-` 或 `记录-` 解释为当前产品行为。
