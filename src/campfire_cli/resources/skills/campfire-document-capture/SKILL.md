# Campfire 文档沉淀

保留问题、结论、证据、适用边界和后续行动，不复制聊天与调试流水。用户直接要求沉淀、接受提议或给出范围明确的持续授权时，不重复询问是否写文档。

## 写入门禁

正式写入必须同时满足以下条件。允许沉淀不等于允许猜测缺失信息，CLI 校验通过也不代表业务事实已经核验。

1. **授权明确**：本次创建或修改在用户授权范围内；已有授权不重复询问。没有授权时先提议，不静默落盘。
2. **目标明确**：写入对象与位置唯一；覆盖、合并或归属存在关键歧义时先确认，不猜目标。
3. **表述有依据**：事实有来源，计划、建议和推断明确标注。记录用户计划不必检查无关源码；声称项目已实现则核对对应证据。缺少关键事实时先获取或询问，不编造。

条件已满足就进入下方最短路径，不额外增加命令或审批。门禁同样适用于直接 Edit 正文；归档、删除等仍遵守专项授权要求。

## 上下文与契约

apply 的 `--path` 必填，支持 Workspace 根相对路径或 Workspace 内绝对路径，不相对于 cwd。创建时可省略前缀与 `.md`，最终以 `target` 为准。新建契约未知时只查询目标 `document profile show <type>`，不从 tree 或全部 Profile 开始。

## SOP

### 流程总览

门禁满足后按本次修改选择一条路径；仅补充缺少的上下文，不依次执行所有分支。

```text
本次文档操作
├── 只改人工正文 → Read → Edit → 核对修改区域
├── 创建文档 / 修改结构
│   ├── 契约已知 → 直接 apply 预览
│   └── 契约未知 → 新建查 Profile / 已有文档 inspect → apply 预览
├── 只改标题 → rename 预览
└── 跨领域移动 → move 预览

CLI 预览结果
├── 有问题 → 修正可确定输入；关键事实缺失则询问，暂不写入
└── 无问题且已授权 → 原输入 + 返回哈希（改路径时另带计划摘要）+ confirm
    ├── 写入失败 → 报告问题，停止后续操作
    └── 写入成功 → 新建时按 target 补正文 → 执行实际 follow_up → 回报
```

### 执行步骤

- **已知路径，只改人工正文**：读取局部内容与尚未知的局部规则 → 最小 Edit → 核对修改区域。不加载 bootstrap，不调用 apply，不改 Frontmatter 或自动生成区。
- **已授权、主题及目标目录明确的新文档**：契约已知时直接 apply 预览 → 无问题后以相同输入加返回哈希和 `--confirm` → 按返回的 `target` Edit 正文 → 执行实际 follow_up。没有重复、覆盖或事实疑点时不固定查询 Workspace、Project、全部 Domain 或现有文档集合。
- **已知文档修改结构**：契约已知直接 apply；字段或枚举未知先 inspect 一次。只改标题使用 rename，跨 Domain 移动使用 move，不手改受管结构。

### 命令示例

以下示例假设 Workspace `demo` 已有 `mynote/开发实践` Domain，用户要求沉淀一条明确知识；目录和字段值须以当前 Workspace 与 Profile 为准。

```bash
campfire --workspace demo document apply --path "mynote/开发实践/安装验证" --type knowledge --set 'description=安装后通过版本命令验证可用性'
campfire --workspace demo document apply --path "mynote/开发实践/安装验证" --type knowledge --set 'description=安装后通过版本命令验证可用性' --expected-hash missing --confirm
```

新建预览返回 `status: planned`、`expected_hash: missing`、`target`；确认返回 `status: applied`、`write_performed: true`。已有文档使用实际返回哈希，不套用 `missing`。创建后必须补正文，保留 Frontmatter；没有 `--body` 参数。仅结构创建成功不等于文档内容已经完成。

文档关系唯一事实源是 Frontmatter 的 `related_docs`。Agent 只通过 apply 修改它，例如 `--set 'related_docs=["[[mywork/项目/技术-登录.md]]"]'`；路径必须是 Workspace 根相对路径，保留 `.md`，不加别名或锚点。正文链接只是正文，不解析、不维护，也不为了关系同步改正文。反向关系由索引计算，不在目标文档重复填写。

rename、move 或 apply 导致已有文件路径变化时，先预览完整影响范围，再用同一输入加返回的 `--expected-hash <hash> --expected-plan <digest> --confirm`。计划变化就重新预览，不绕过保护。

### 创建与更新文档关联

- **创建**：有依据且目标已存在时，在创建的 apply 中一并填写 `related_docs`；没有明确关联就省略，不要求先搜索整个 Workspace。
- **更新**：不涉及关系时不传该字段；要添加或解除关系，先读取来源文档的原列表，保留无关项并去重，再提交完整列表。`--set related_docs=...` 是整体替换，不是追加；只有明确清空全部出向关系时才传空数组。
- **任务产出**：为一个明确任务创建需求、技术方案或问题记录时，先创建文档，再在授权范围内把返回的 `target` 加入任务的列表；不同时给新文档补一条对称关系。若本次意图是从记录等文档关联任务，则直接在该来源文档填写任务路径，不强制改变方向。
- **查看与解除**：需要关系上下文时用 inspect 同时查看 outgoing、incoming、unresolved。反向关联由索引计算；解除入向关联要修改对应来源文档，不能修改索引或目标文档的列表来代替。
- **失败与边界**：关联目标尚未创建时先完成目标创建；目标不明不猜测。新文档成功但任务关联失败时报告两步的实际结果，只修复失败步骤。纯正文更新不维护关系，也不自动改变关联文档的状态。

## 异常与停止条件

只执行与当前风险有关的检查，不逐项重跑已经明确的上下文：

- Workspace 或归属缺失：按需使用 `campfire-context-bootstrap`；候选不唯一时集中询问。没有合适 Domain 先提议创建，不能直接写在 Space 根。
- 写项目当前事实：核对相关源码、配置、测试或日志。无法访问时明确证据限制，不能把计划写成已实现。通用知识不检查无关项目。
- 发现同主题权威文档、潜在重复或覆盖：先读相关内容，决定更新或创建；合并、覆盖权威结论或归属有歧义时询问。
- 必填业务信息缺失：依据返回的 issues / missing_fields 一次补齐可确认的信息，其余询问，不为通过校验编造值。
- 归档、删除或超出既有授权范围：取得用户对具体对象的明确同意。`--confirm` 只是 CLI 写入确认，不替代用户授权。
- 并发变化：重新读取并核对，不重放旧哈希强行覆盖。

事实必须区分：证据已验证、用户提供、目标方案、讨论建议与历史记录。推断明确标注，不包装成当前事实。正文模板从目标 Domain 向父 Domain 查找最近同名模板；找不到用最小结构，不虚构章节内容。模板的创建和修改需要用户要求或确认。

Project 的物理归属由 CLI 解析，不表示自动写入任务的 `related_project`。字段与枚举归 Profile，目录约定和模板归 Workspace，Skill 不重复维护。

## 完成条件与回报

实际写入后，仅执行结果给出的 scoped follow_up，不固定转交 Maintenance Skill，不重复 check 或全库扫描。纯正文编辑不改变受管关系，不需要为正文链接执行 sync。若返回文件已写入但索引刷新失败，修复索引问题后重新查询，不重复执行写入。

关键歧义优先在当前对话询问；已有待确认记录授权或用户认可的持续记录约定时，才按当前 `governance.human_request_root` 和 human-request Profile 创建待确认文档。仅配置目录不等于授权，无法立即询问也不自动取得写入权限。待确认文档只记录已知事实与问题，不写成正式结论；用户回答后更新正式文档，归档仍需明确同意。

主动发现值得沉淀的内容可以合并提议，但提议本身不构成写入授权。完成后回报最终路径、实际结果、证据限制和未解决问题。
